# Release pipeline security

Security review date: 2026-07-21. The release workflow is generated by
cargo-dist 0.32.0, as pinned by `cargo-dist-version` in `dist-workspace.toml`.
Generator-backed fixes belong in that file; unsupported workflow changes would
otherwise be lost the next time `dist init` or `dist generate` runs.

## cargo-dist 0.32 configuration findings

The v0.32 configuration supports `github-action-commits`, which overrides an
action's generated version with a full commit SHA. The following immutable
release commits are configured and reflected in `release.yml`:

- `actions/checkout` v6.0.2: `de0fac2e4500dabe0009e67214ff5f5447ce83dd`
- `actions/upload-artifact` v7.0.1: `043fb46d1a93c77aae656e7c1c64a875d1fc6a0a`
- `actions/download-artifact` v8.0.1: `3e5f45b2cfb9172054b4087a40e8e0b5a5461e7c`
- `actions/attest` v4.2.0: `f7c74d28b9d84cb8768d0b8ca14a4bac6ef463e6`

This closes the mutable-action-reference item. Updating an action now requires
an intentional config change and workflow regeneration.

The other relevant v0.32 extension points do not cover the remaining findings:

- `github-custom-job-permissions` controls only user-defined custom jobs, not
  cargo-dist's built-in `plan`, build, `host`, or `announce` jobs.
- `github-build-setup` inserts steps before local artifact builds. It cannot
  replace or verify the installer executed earlier by `plan`.
- Custom phase jobs are additive; they cannot replace built-in steps or their
  environment. `allow-dirty = ["ci"]` can opt out of generated-workflow checks,
  but that is a hand-maintenance escape hatch rather than a security setting.

The conclusions above are based on the cargo-dist 0.32 config reference and the
v0.32.0-generated workflow. No local `dist` or `cargo-dist` executable was
available for an additional schema/help check.

## Open findings and residual risk

### Workflow-wide `contents: write`

Open: cargo-dist 0.32 has no setting for the permissions of built-in jobs. The
top-level `contents: write` therefore remains inherited by `plan`, both build
jobs, and `announce`. A compromised action, build script, or dependency in one
of those jobs could use the workflow token to modify repository content or
releases, with the greatest exposure on tag-triggered release runs.

The risk is narrower than a fully unscoped workflow: checkouts use
`persist-credentials: false`, and the actual `host` publishing job declares its
own permissions (`attestations: write`, `contents: write`, and `id-token: write`)
at approximately line 227. Nevertheless, the top-level write grant remains
unnecessarily available to the other built-in jobs.

### Unverified cargo-dist bootstrap

Open: cargo-dist 0.32 always generates the pinned-version installer as a remote
`cargo-dist-installer.sh | sh` command in `plan`; it has no setting for an
installer digest, alternate bootstrap command, or verification step. The
resulting executable is cached and later run by `build-global-artifacts` and the
write-capable `host` job.

HTTPS, the fixed `cargo-dist-version = "0.32.0"`, and cargo-dist's immutable
GitHub release reduce accidental substitution risk. Pinned artifact actions and
download-artifact's integrity checking protect the cached artifact in transit,
but they do not independently establish that the executable initially produced
by the remote installer is the expected cargo-dist binary. Compromise of the
installer origin or release asset could therefore reach the publishing job.

### `GH_TOKEN` in non-publishing jobs

Open: cargo-dist 0.32 has no setting to remove or scope the generated `GH_TOKEN`
environment entry on built-in jobs. It remains present in `plan`, both build
jobs, and `announce`, as well as `host`. In combination with inherited
`contents: write`, code executing in a non-publishing job can access a token with
repository write capability on release runs.

## Existing protections and durable options

Sigstore-backed GitHub artifact attestations remain enabled with
`github-attestations = true` and run in the separately permissioned `host` job.
They provide verifiable provenance for released assets, but they do not make an
unverified bootstrap safe: a compromised producer can attest compromised output.

No stopgap edit was made for the three open findings, and `release.yml` does not
diverge from expressible cargo-dist configuration. Resolving them requires one
of these ownership decisions:

1. Keep `cargo-dist-version` pinned, set `allow-dirty = ["ci"]`, add a prominent
   divergence warning, and hand-maintain the workflow (including reapplying and
   reviewing changes during upgrades).
2. Stop using cargo-dist to generate the release workflow and own a custom
   least-privilege pipeline.
3. Upstream cargo-dist features for built-in job permissions/environment and a
   digest-verified or replaceable bootstrap, then regenerate after adoption.

## Accepted risk: no local authentication on the dashboard (audit finding 5)

**Status:** deliberately deferred, owner decision 2026-07-21. **Update
2026-08-26:** the primary intended mitigation has since shipped (audit wave 1,
H-5) — the dashboard now mints a random session token at startup, includes it
only in the printed bootstrap URL, and requires it on every route outside that
page; `--no-auth` restores unauthenticated serving explicitly. The analysis
below is preserved as written when the risk was accepted; concurrent-launch
caps also landed, while cookie exchange and spend limits remain open ideas.

The dashboard binds to loopback and defends against cross-origin browser
requests with a CSRF token, but the token is embedded in the unauthenticated
index page. Any other process or user account on the same machine can therefore
fetch the index, read the token, and then drive the dashboard: list and read
books and reviews, control jobs, and launch provider requests that spend money
using remembered or environment-supplied keys.

This is accepted rather than fixed because the deployment is a single-user
desktop where any local process able to reach the socket could equally read the
key files directly, and because the realistic mitigations — a startup token in
the opened URL, or a login prompt — put a credential step in front of daily,
non-technical use for no gain against that threat model.

**Revisit if any of these become true:**

- the dashboard is ever bound to anything other than loopback, or exposed
  through a tunnel or port forward;
- the machine becomes multi-user, or runs untrusted local software;
- provider spend per run grows enough that an unattended local caller could
  incur meaningful cost.

The intended fix, in preference order, is a random token minted at startup and
included in the auto-opened URL, exchanged for an `HttpOnly; SameSite=Strict`
session cookie, plus caps on concurrent jobs, upload size and provider spend.
The rate limits are worth adding independently of authentication.
